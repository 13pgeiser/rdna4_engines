# AGENTS.md

Host-orchestration repo for serving LLMs on a local AMD Radeon AI PRO R9700 (gfx1201 / RDNA4) box. The top-level `.sh` entry points, `common.sh`, the two `Dockerfile.fastflowlm*` files, and `radiance-vllm-mxfp4-scripts/` are the local (first-party) flow; the seven directories are **git-subtree checkouts of external repos — not first-party code**.

## Subtrees (do not hand-edit)

- `llama.cpp/` — ggml-org/llama.cpp (master)
- `radiance-vllm-mxfp4/` — ggz14/radiance-vllm-mxfp4 (main) — the vLLM + MXFP4 stack
- `radiance/` — StillDeadcode/radiance (main) — a C++/HIP engine, distinct from `radiance-vllm-mxfp4/`
- `libr4d/` — StillDeadcode/libr4d (main)
- `hipfire/` — warpfront/hipfire (master)
- `FastFlowLM/` — ROCm/FastFlowLM (main) — the NPU runtime (Ryzen AI XDNA2; `flm` CLI); its `Dockerfile` is a CI build environment, not a runtime
- `FLM_Q4NX_Converter/` — ROCm/FLM_Q4NX_Converter (main) — the official GGUF → Q4NX converter (`convert.py` + per-arch `configs/`, incl. `qwen3.5_a3b` for the 35B-A3B MoE geometry); runs in its own torch venv via `setup_venv.sh`

Sync all seven with `./git.sh` (runs `git subtree add` or `pull` per dir). Changes belong in the upstream repos. `radiance-vllm-mxfp4-scripts/` is local, not a subtree.

## The local flow (top-level scripts)

All five servers listen on port **9931** (not the upstream defaults). The vllm/llama/hipfire entry scripts start by writing a 210 W GPU power cap to sysfs via `sudo` (that line is commented out in `run_radiance.sh`).

- `./run_radiance-vllm-mxfp4.sh [rocm7|rocm10] [--bench]` — the radiance-vllm entry point (default **rocm10**). Prepares **`/models/radiance-vllm-mxfp4`** (git-clones `amd/Qwen3.8-27B-Quark-AWQ-MXFP4` and `tcclaviger/Qwen3.8-27B-DFlash2-FP8`, then builds the two derived variants below; `/models` is filesystem root — absolute, not `~/models`). Builds the docker image **only if missing** (`radiance-vllm-mxfp4:$(cat radiance-vllm-mxfp4/VERSION)` for rocm7; `rocm10-radiance-vllm-mxfp4:…` for rocm10, via a sed-rewritten `Dockerfile.rocm10` with a ROCm 10.0 base), writes the power cap, and serves via `radiance-vllm-mxfp4/serve-mxfp4.sh` (TP=1, foreground). Docker, not podman. With `--bench` it instead serves detached (`DETACH=1`), waits for `/health` (900 s timeout), runs the vLLM bench client (`vllm bench serve`, 100 random prompts), then stops the container.
- `./run_radiance.sh` — drives the **C++ `radiance` engine** (the `radiance/` subtree, not the vllm one). Same GPU-arch gate as `run_hipfire.sh` (PCI ID via `/sys`, dmesg fallback; **gfx1201** or **gfx1152** only, early exit otherwise). Builds `local/radiance` via `radiance/Dockerfile` with `GPU_TARGETS="gfx1201;gfx1152"` (multi-target — the kernel library is baked per target, libr4d for gfx12 / libr3d for gfx11, and the image test stage's `docker/llvm-check.sh` needs the `libr4d` target, which a gfx11-only build does not produce; one image serves both boxes) **only if missing or the image's `radiance.gpu-targets` label does not name the detected arch**; it builds with `TEST_EXCLUDE=.*` so the ~400 s in-image host test suite does not run (this box runs over its CPU budgets and a few host-only tests fail on it; `docker/llvm-check.sh` still runs and gates the build, and the suite can be run out-of-band). Downloads `qwen3.8-27b-mxfp4.rad` from `StillDeadcode/qwen3.8-27b-mxfp4` into `/models/rad` and serves on 9931. Model 1 (27b, arch plugin `qwen35_fp8`) **cannot start on gfx1152**: its op set (gated-MX GEMM, `qk_norm_rope_gate`, head_dim-256 paged attention, imrope/axial rope, `attn_dense`, `rope_table`, `gate_quant_fp8`, `add_rmsnorm`) exists only in `libr4d` (RDNA4) / `libhalo` (gfx1151), not `libr3d` (which serves gfx1152) — the engine aborts at startup listing the kernel-less bands; that model is gfx1201-only until the ops are ported to `libr3d` upstream (the MoE models 2–4 are the gfx1152 candidates).
- `./run_fastflowlm.sh [tag]` — the FastFlowLM entry point (**gfx1152 box only**, early exit elsewhere). FLM runs on the Ryzen AI **XDNA2 NPU**, not the GPU: besides the same GPU-arch gate it requires the `amdxdna` module loaded and a `/dev/accel/accel*` node (kernel 7.0+ in-tree or `amdxdna-dkms`). The image **`local/fastflowlm-src:<rev>`** is built from the **`FastFlowLM/` subtree** via the local **`Dockerfile.fastflowlm-src`** **only if missing or the image's `flm.src-rev` label differs** — `<rev>` is the subtree's git tree hash (`HEAD:FastFlowLM`), so a `./git.sh` sync that moves `FastFlowLM/` builds a fresh image, old ones survive for A/B testing, and unrelated commits reuse it. The build mirrors CI's XRT-portable leg: it compiles in the public `ghcr.io/rocm/fastflowlm/build-environment:debian13` image with the `linux-portable` preset (install into `/opt/fastflowlm`, `flm` renamed to `flm-real`, `flm-wrapper.sh` to `flm`), cloning the two `third_party` submodules (empty gitlinks) at their pinned revisions; a first build per subtree state is a full compile, so it is slow. `Dockerfile.fastflowlm` (the official release tarball into `debian:13` + libcurl4t64 libstdc++6 libgomp1 libuuid1) is kept but no longer used by the script; the repo's own `FastFlowLM/Dockerfile` is only a CI build environment. Models are `flm pull`ed into host `/models/flm` (bind-mounted at `/models`, `FLM_MODEL_PATH`; pull is a no-op when present). Menu over the script's tags (positional arg or interactive; non-interactive default is index 1). Serves foreground (container `fastflowlm_server`, `--network host`, `--device /dev/accel`, `--ulimit memlock=-1` — NPU needs unlimited memlock — `seccomp=unconfined`) via `flm serve <tag> --host 0.0.0.0 -p 9931`. No power cap (NPU). The `ornith:35b-a3b` tag is in no FLM registry: on first run the script downloads the public Ornith GGUF (Q4_K_M, ~22 GB) plus mmproj, converts to Q4NX via the `FLM_Q4NX_Converter/` subtree (its own venv; slow CPU convert), repairs the ssm alpha/beta tables the converter emits in a form the engine cannot load — the converter packs them as I8 and stashes the dequantized values in transposed `.bf16.` side-entries while the qwen3.6-moe NPU2 engine wants a plain BF16 [2048, 32] main entry, so unpatched the engine segfaults in `qwen3_6_reorder_cpy` (repair: `fastflowlm-scripts/fix_q4nx_ssm.py`, in-place, idempotent) — and registers it locally — model files in `/models/flm/models/Ornith-1.5-35B-A3B`, a catalog override in `/models/flm-ornith-catalog` (mounted at `/opt/flm-ornith-catalog`, outside `/models`, passed via `FLM_CONFIG_PATH`), a copy of `Qwen3.6-35B-A3B-NPU2`'s xclbins under the new name (host `/models/flm-xclbins`, bind-mounted over `/opt/fastflowlm/xclbins`), and a `flm_version` stamped into the copied `config.json` (without it the compatibility check reads "0.0.0", marks the model Outdated and runs a file-verification pass a local model has no records for). The model's `config.json`/`tokenizer.json`/`tokenizer_config.json` must be in **FLM registry format** — a flat config with `vision_*_engine_xclbin_name`, `vision_model_weight`, NPU `addr_*` fields and `QWEN3_6_MOE_*` constants, and a tokenizer_config with no embedded `chat_template`: the HF-native files the Ornith repo ships lack those fields and the engine segfaults right after `Loading model` (a null-deref in the missing config fields). They are taken from a pulled `Qwen3.6-35B-A3B-NPU2` model if present, else the three small files are fetched straight from the registry (`file_url` in the image's `model_list.json`) — no 35 GB pull needed; `chat_template.jinja` is the froggeric fixed template shared with the radiance-vllm flow (auto-downloaded from `froggeric/Qwen-Fixed-Chat-Templates` if missing). `ORNITH_PKG=<hf-repo>` fetches a prebuilt NPU2 package instead of converting (run through the same repair; note `Atomic-Germ/Ornith-1.5-35B-A3B-NPU2` is NOT loadable by this engine — Q8-repacked tensors plus an extra MTP layer 40). It runs on the same `qwen3.6-moe` NPU2 engine (identical geometry; ~20 tok/s decode, ~127 tok/s prefill on ai350). `VISION=0` skips the vision tower, `ORNITH_FORCE` overrides the converter's arch detection; re-runs are no-ops.
- `./run_llama.sh [model]` — builds `local/llama.cpp:latest` via `llama.cpp/.devops/rocm.Dockerfile` **only if missing** (`AMDGPU_TARGETS=gfx1201`), writes the power cap. The model is a menu (positional arg, or interactive; non-interactive default is index 1) over GGUFs under `/models/llama.cpp`; serves foreground (`docker -it`, container `llama_cpp_server`) on 9931.
- `./run_hipfire.sh [tag]` — the hipfire entry point (default tag **`qwen3.8:27b-mq4-xts`**; a menu now offers two tags). First a GPU-arch gate: maps each AMD DRM card's PCI ID from `/sys` (R9700 `0x7551` → gfx1201, Ryzen AI 7 350 / Krackan `0x1114` → gfx1152), with the amdgpu dmesg IP block version (`<gfx_v…>`; plain `dmesg`, `sudo dmesg` fallback) as a family fallback for unknown IDs (`gfx_v12_0_*` → gfx1201, `gfx_v11_5_*` → gfx1152 — the IP version alone is not the target, e.g. both the R9700 and the Krackan report a plain `x.y.0`), and exits early unless the box has exactly one of **gfx1201** or **gfx1152**. Builds `local/hipfire` via `hipfire/Containerfile` **only if missing or the variant differs** (checked via the image's `dev.hipfire.variant` label): `--target runtime` on gfx1201, `--target full` on gfx1152 — no gfx1152 kernel pack is baked (baked arches are gfx1100/gfx1151/gfx1201) and the slim runtime has no hipcc, so a missing kernel is a hard error; the full image JITs each such route once into the `hipfire-kcache` volume. Multi-stage; no GPU needed at build time. Pulls the registry model into host `/models/hipfire` (bind-mounted at `/root/.hipfire/models`), writes a default `reasoning_effort` (env `REASONING_EFFORT`, default **medium**) into the persistent `hipfire-home` volume, and on gfx1152 also sets per-model `dflash_mode off` (the registry auto-enables the 27B DFlash draft, whose MQ4G256V2 batched lm_head verify is not admitted on gfx1152 — pre-warm fails and every request 400s without it), writes the power cap (gfx1201 only), and serves foreground (container `hipfire_server`) on 9931.

## Checkpoint pipeline (radiance-vllm)

AMD's `Qwen3.8-27B-Quark-AWQ-MXFP4` **does not load as-is**: its bf16 MTP head is mis-declared in the quark config (fails with `AssertionError: Attempted to load weight (5120, 10240) into (5120, 5120)`). The rewrite is mandatory:

1. `radiance-vllm-mxfp4-scripts/fp8_mtp.py <src> <dst>` → `Qwen3.8-27B-MXFP4-mtpfp8` (needs **torch**; `run_radiance-vllm-mxfp4.sh` spins a throwaway venv in `/models` for it)
2. `radiance-vllm-mxfp4-scripts/mtpfp8-pertoken.py <src config.json> <dst config.json>` → `-pertoken` variant (config-only, no torch; rewrites the 8 `mtp.*` `input_tensors` to per-channel; prints "expect 8")

Note: `radiance-vllm-mxfp4-scripts/fp8_mtp.py` and the copy in `radiance-vllm-mxfp4/fp8_mtp.py` **differ**; the entry script uses the `radiance-vllm-mxfp4-scripts/` one.

`radiance-vllm-mxfp4-scripts/chat_template.jinja` is auto-downloaded from `froggeric/Qwen-Fixed-Chat-Templates` if missing; `run_radiance-vllm-mxfp4.sh` mounts it into the container.

## Radiance stack

The local flow builds its own image (`radiance-vllm-mxfp4:$(cat radiance-vllm-mxfp4/VERSION)`, currently 0.13.0) via `radiance-vllm-mxfp4/Dockerfile` — this differs from the subtree README's quickstart (pulls published `stilldeadcode/vllm-radiance:0.9.3`). For the radiance internals (knobs, troubleshooting, performance, ParoQuant, TP=3 padding), the subtree docs are the authoritative reference: `radiance-vllm-mxfp4/README.md`, `PERFORMANCE.md`, `PAROQUANT.md`, `DOCKERHUB.md`, `TP3_PADDING_PLAN.md`, `MXFP4-NOTES.md`, `FASTBOOT.md`.

- All serving knobs are `${VAR:-default}` env overrides; nothing needs editing. `DRY_RUN=1 ./serve-mxfp4.sh` prints the container command; `./serve-mxfp4.sh --help` is the short reference.
- `run_radiance-vllm-mxfp4.sh` `sed`-rewrites the `--override-generation-config` line inside `serve-mxfp4.sh` on every start (top_k 20), then reverts the file via an `EXIT` trap (`git checkout`) when the script terminates — the local diff is transient, present only during the serve run.
- TP is auto-detected (largest of 8/4/2/1 that fits); 3/6/12 are never auto-picked (GDN head divisibility) and TP=3 is available only via explicit dummy-head padding (`RADIANCE_TP_PAD=3`). Cards below `MIN_GPU_MIB=8192` are excluded so the box's 2 GiB iGPU render node is never picked.
- The stock libr4d kernel in published images **NaNs this model's GDN path** (perplexity in the hundreds of thousands); the launcher builds a pinned libr4d (`AUTO_R4D=1`, default). Don't run with `AUTO_R4D=0` unless you know why.

## libr4d

HIP kernel library for gfx1201. Entry-point names encode the exact geometry (compile-time constants; mismatches are rejected, not run). `r4d.select()` / `r4d.kernels()` answer "is there a kernel for this shape" — `None` means fall back to non-R4D paths. Build: `./build.sh` (needs `hipcc`, same ROCm as the runtime; `radiance-vllm-mxfp4/Makefile`'s `make r4d` clones the pinned libr4d and compiles it inside the image so it matches). Adding a kernel: 6-step process in `libr4d/README.md` (registry row in `r4d_registry.hip` is what makes it visible).

## hipfire

RDNA-native LLM inference engine (Rust + HIP + Redline; ROCm is dlopen'd at runtime). See the `./run_hipfire.sh [tag]` entry point above for the build/pull/serve flow. The `local/hipfire` image bundles the daemon, native CLI, and exact-source registry kernel packages compiled for the Containerfile's baked arches (`gfx1100 gfx1151 gfx1201` by default; other arches rely on JIT in the `full` variant). Runs need GPU passthrough (`--device /dev/kfd --device /dev/dri --security-opt seccomp=unconfined`); the JIT kernel cache is the named volume `hipfire-kcache` (`/var/cache/hipfire`); the OpenAI-compatible serve API is on port **9931**. The `Containerfile` base is `rocm/dev-ubuntu-24.04:7.2.4`; do not downgrade (gfx1151 needs ROCm 7.2+; gfx1201 needs 6.4+). If a build reports missing `hipcc`/HIP headers, switch the base tag to `7.2.4-complete`.

## Verification

No CI, no pre-commit, no top-level test suite. Subtree checks that need no GPU: `tp3pad_selftest.py` (radiance-vllm-mxfp4), `make verify IMAGE=<rocm-image>` (libr4d). Otherwise the check is "does the server answer a request" — see the subtree READMEs.
